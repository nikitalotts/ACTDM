# Wikipedia: полный прогон экспериментов

Порядок действий от чистого кластера до финальных метрик. Все команды — из
корня репозитория. Стадии `run_wikipedia.sh` зависят друг от друга через
артефакты на диске: каждую следующую запускать после того, как отработала
предыдущая (что где появляется — написано ниже).

## Раскладка по дискам (Харизма: home 3 мес / scratch 1 мес, NVMe)

Принцип: на scratch — только то, что дешево скачать заново; всё, без чего
прогон встанет, — в home. Раскладку задает `hf_env.sh`, подключенный всеми
точками входа; настраивать руками ничего не нужно, но при старте каждый
скрипт печатает `HF_HOME=... HF_DATASETS_CACHE=...` — стоит сверить, что
прогрев и задания видят одни и те же пути.

- `HF_HOME=~/hf_cache` (**home**, ~13 GB): модели, токенизаторы и скрипты
  метрик. Scratch чистят ежемесячно, а без этих кэшей eval падает уже после
  дней обучения — поэтому они лежат там, где переживут чистку.
- `HF_DATASETS_CACHE=/scratch/$USER/hf_datasets` (**scratch**, ~30 GB): сырой
  кэш дампа wikipedia. Нужен только на стадии `data`, после нее удаляется.
- `<репо>/datasets/wikipedia` (**home**): нарезанный датасет, статистики
  энкодера, декодеры, классификаторы. Симлинк на scratch не делать — при
  чистке пришлось бы переобучать декодеры и классификаторы.
- `checkpoints/`, `generated_texts/`, `wandb/` (**home**): чекпоинты
  невосстановимы без повторного обучения. Место под них: у диффузии
  save_top_k=5, у gpt 2, плюс служебный `last.pth` для дозапуска — порядка
  15 GB на диффузию и 13 GB на gpt.
- Репу на кластер класть **гитом** (`git clone`), а не заливать с Windows:
  CRLF ломает `.sh`.
- Переопределение любого пути — обычный `export` перед запуском: заданные
  снаружи значения ничем не перетираются.
- home тоже не вечен (3 мес): финальные json из `generated_texts/` и лучшие
  чекпоинты по завершении забирать к себе.

## 0. Локально: закоммитить и запушить

Должны уехать: `run_wikipedia.sh`, `run_flags.sh`, `prefetch_offline.py`,
`disk_report.sh`, `diffusion_holder.py`, `RUNBOOK.md`.

## 2. Смоук-прогон (рекомендуется, ~полдня)

Проверяет весь пайплайн до первых метрик, прежде чем жечь GPU-дни. Смоук-режим
(`SMOKE=1`) режет обучение до 200 шагов и 200 генерируемых текстов, а все
артефакты помечает суффиксом `-smoke`, поэтому боевые он не трогает и не
подхватывает.

```bash
NUM_TEXTS=200000 ./run_wikipedia.sh data
```

```bash
./run_wikipedia.sh stats        # дождаться datasets/wikipedia/statistics/*.pt
```

```bash
./smoke_test.sh decoder         # дождаться decoder-*-smoke.pth
```

```bash
./smoke_test.sh diffuseq        # ~30 мин
```

```bash
./smoke_test.sh gpt             # ~30 мин, ни от чего не зависит
```

В slurm-логе проверить: SOURCE/TARGET режутся по 64 токена, примеры генерации
не мусор, метрики посчитались, лосс падает.

**Обязательная уборка после смоука** — иначе полный прогон подхватит
смоук-датасет (у него нет суффикса, в отличие от остальных артефактов):

```bash
rm -rf datasets/wikipedia checkpoints/*-smoke datasets/wikipedia/*-smoke.pth generated_texts/*-smoke
```

## 3. Полный прогон

### 3.1 Данные (login-нода, интернет)

```bash
./run_wikipedia.sh data
```

Появится `datasets/wikipedia/{train,validation,test}`. Сырой кэш дампа больше
не нужен: `rm -rf ~/.cache/huggingface/datasets/wikimedia___wikipedia*`

### 3.2 Статистики энкодера

```bash
./run_wikipedia.sh stats
```

Готово, когда появились `datasets/wikipedia/statistics/encodings-bert-base-cased-{mean,std}.pt`.

### 3.3 Декодеры (2 задания параллельно)

```bash
./run_wikipedia.sh decoders
```

Готово: два `datasets/wikipedia/decoder-*.pth` (один с `-conditional` для
genie, один безусловный для остальных).

### 3.4 Диффузии и GPT (4 обучения параллельно)

```bash
./run_wikipedia.sh diffusion    # genie, diffuseq, unconditional
```

```bash
./run_wikipedia.sh gpt          # можно было запустить сразу после 3.1
```

Диффузии можно пускать и по одной — `./run_wikipedia.sh diffuseq` (то же для
`genie` и `unconditional`), когда не нужно занимать очередь всеми тремя сразу
или когда надо перезапустить только одну.

Это самая долгая стадия. **Бюджет сравнения — 87500 оптимизаторных шагов при
эффективном батче 512, то есть 44.8 млн увиденных примеров** (константа
`COMPARISON_STEPS` в `create_config.py`). Изначально планировалось 150k, но
diffuseq вышел на плато и ресурсов проекта на 150k не осталось; genie, diffuseq
и unconditional остановлены на 87500, и посчитаны именно эти числа. Обрезка
законна, потому что `lr == min_lr == 2e-4` у всех четырёх подходов — косинус
выродился в константу, и первые 87500 шагов идут по той же траектории
(проверяется тестом `test_lr_schedule_is_flat_so_truncating_the_budget_is_legal`).

У трёх диффузий конфиг намеренно остался 150k — они уже досчитаны, прогон
снимали руками после строки `Save model to: .../87500.pth`. **У gpt бюджет
записан в конфиг**: прогон завершается сам на шаге сравнения. Ловить момент
руками там нельзя — при лимите задания 75 ч и ~170 ч счёта дозапусков три.

Время по стене на 4xV100-32GB: gpt ~170 ч (3 дозапуска), diffuseq 53 ч (факт),
genie 41 ч (факт), unconditional 31 ч (факт). Дозапуск — просто отправить
`./run_wikipedia.sh gpt` заново: обучение продолжится с
`checkpoints/<prefix>/last.pth`. У gpt он пишется **каждые 2500 шагов** (~5 ч),
отдельно от eval: при лимите 75 ч терять сутки счёта из-за редкого сохранения
нельзя. Нумерованные чекпоинты и метрики — каждые 12500 шагов, как у диффузий
(7 точек на бюджете, `save_top_k=7`, то есть на диске остаются все семь и шаг
87500 гарантированно переживает отбор). Место под чекпоинты gpt — **~34 ГБ**
(7 x 4.3 ГБ + `last.pth`); если в home тесно, досчитанные диффузии можно
прорядить, оставив `87500.pth`. guidance отдельно не обучается: он использует
чекпоинт unconditional.

### Точность: bf16 или fp16 (замерить ДО запуска gpt)

По умолчанию обучение идёт в bf16 — так обучены три диффузии. Но V100 это
Volta (sm_70), а тензорные ядра для bf16 появились только с Ampere: на V100
bf16-матмул идёт примерно со скоростью fp32, тогда как fp16-ядра на этой карте
есть. По замеренному шагу gpt выходит около 9 TFLOPS на карту — уровень fp32
(пик 15.7), а не fp16 (пик 125), так что запас может быть кратным. Проверяется
пробником, двумя заданиями по ~20 мин:

```bash
AMP_DTYPE=bf16 ARCHS=gpt MAX_BATCH=128 sbatch find_max_batch.sh
```

```bash
AMP_DTYPE=fp16 ARCHS=gpt MAX_BATCH=128 sbatch find_max_batch.sh
```

Сравнить строку батча 128 в таблицах `slurm_logs/<jobid>-find_max_batch.log`
(`max_batch_report.json` второе задание перезапишет — смотреть лог). Если
fp16 быстрее — запускать обучение с `AMP_DTYPE=fp16 ./run_wikipedia.sh gpt`
(`sbatch` экспортирует окружение целиком). `GradScaler` в `gpt2_holder`
создаётся всегда, так что fp16 поддержан полностью; значение попадает в лог
строкой `[GPT2] autocast dtype:`. В имя чекпоинта точность НЕ входит — на
первых шагах стоит посмотреть, что лосс падает так же, как в bf16.

### 3.5 Классификаторы guidance (после unconditional-диффузии)

```bash
./run_wikipedia.sh classifiers
```

Три схемы (shuffled/augmented/combined), каждая пишет свой
`datasets/wikipedia/conditional-encoder-*-64x64-*.pth`. augmented и combined
загружают последний чекпоинт безусловной диффузии — поэтому только после 3.4.
Вариант с TIME_SCALE: `TIME_SCALE=1000 ./run_wikipedia.sh classifiers`
(тогда и eval запускать с тем же TIME_SCALE; несовпадение поймается ошибкой).

**Бюджет — фиксированный пул, как на rocstories.** Рецепт ВКР воспроизводится
буквально: 88160 пар (2755 батчей по 32 с `drop_last`) и 13 проходов по ним —
35815 оптимизаторных шагов, 1.15 млн увиденных пар. Совпадает не только
итоговый объём, но и число различных примеров, и число повторов каждого.

На wikipedia пул **отбирается детерминированно** из шарда
(`take_fixed_subset` в `data/dataset.py`, сид `CLASSIFIER_SUBSET_SEED = 0`), и
тем же сидом засеян порядок батчей. Это существенно: шард — около 1.5 млн пар,
бюджет покрывает лишь часть, и без явного отбора «часть» определялась бы
перемешиванием `DataLoader` — своим у каждой из трёх схем и своим при каждом
перезапуске. Три классификатора обучались бы на разных данных, и разница между
схемами перестала бы быть разницей между схемами. Порядок батчей важен по той
же причине: у `shuffled` и `combined` негативы строятся **внутри** батча, то
есть разбиение пула на батчи — часть обучающей задачи.

Обратная сторона: те же 88160 абзацев проходятся 13 раз, переобучение здесь
вероятнее, чем на свежих данных. Поэтому валидация считается в конце **каждой**
эпохи — расхождение train/valid accuracy будет видно в логе и в wandb.

Всё задаётся в `create_config.py` (`CLASSIFIER_TRAIN_EXAMPLES`,
`ROCSTORIES_CLASSIFIER_EPOCHS`, `CLASSIFIER_SUBSET_SEED`) и входит в имя
чекпоинта (`-epochs-13-pool-88160-seed-0-`), так что прогон с другим пулом или
сидом не переиспользует чужой файл. Ожидаемое время на карту с учётом 13
валидаций: shuffled ≈ 5.3 ч, augmented ≈ 5.9 ч, combined ≈ 7.7 ч при лимите
задания 12 ч; три задания идут параллельно. В логе бюджет печатается строкой
`Training budget: ... pairs`.

## 4. Тестирование

### 4.1 Одиночный eval всех подходов

```bash
./run_wikipedia.sh eval
```

Запускает: genie, diffuseq, unconditional, guidance×3 схемы (CG_SCALE=10.0 по
умолчанию, поменять: `CG_SCALE=5.0 ./run_wikipedia.sh eval`), gpt.
Метрики — в slurm-логах, тексты и json — в `generated_texts/<prefix>/`
(у guidance в имени файла схема классификатора и time_scale).

Условные режимы меряются по bleu/bert-score/rouge против референсного
продолжения, unconditional — по mauve/div/ppl.

### 4.2 Для статьи: статистическая оценка (std и 95% CI по сидам)

**Шаг сравнения задаётся явно — `CHECKPOINT_STEP=87500`.** Без него
`restore_parameters` берёт `max(нумерованных)`, а это **разный** шаг у разных
подходов: genie и unconditional доехали до 100000, diffuseq и gpt остановлены
на 87500. Сравнение поехало бы, и в логе это выглядело бы нормально. Если
запрошенного чекпоинта на диске нет — задание падает с перечнем того, что есть.

Сначала убедиться, что шаг 87500 на диске у всех:

```bash
for d in checkpoints/*/; do echo "$d: $(ls "$d" | grep -c '^87500.pth')"; done
```

**Состав набора оценки обязан совпадать у всех подходов — проверить до
прогона.** Дампы 24.10: genie против diffuseq совпадают позиционно 5000/5000, а
genie против guidance — только 1500/5000 при пересечении множеств 4500, то есть
10% примеров разные. Причина в сборе генераций: ранг останавливается на границе
батча за порогом `num_gen_texts // world_size`
(`diffusion_holder.py:1069`), срез по рангам задаётся в
`data/dataset_wiki.py:spilt_data_across_gpu`, а guidance идёт с
`validation.batch_size=128` вместо 500 (`create_config.py:275`, нужна память под
градиенты классификатора). Разный батч и разное число карт двигают границу, и
состав набора расходится.

На выводы это не влияет: при n=5000 и разбросе метрики по примеру ~0.08 замена
500 примеров сдвигает среднее примерно на 0.0005, а измеренные эффекты — сотые
доли. Все замеры `probe_*` сравнимы безусловно: они ходят по своему загрузчику
(`probes/common.py:probe_loader`), одной картой и одним батчем. Но таблицу
статьи так публиковать нельзя.

Поэтому финальная таблица гоняется с **одинаковыми** `validation.batch_size` и
числом карт у всех подходов (для guidance — `GUIDANCE_EVAL_BS=500`, если
хватает памяти; иначе 128 у всех), и перед сведением проверяется:

```bash
python check_eval_alignment.py generated_texts/*/87500-N=50-seed=0-len=1-gs=0.0.json
```

Код возврата 1 означает, что таблицу строить нельзя. Закреплено тестом.

Число сидов — переменная окружения `NUM_SEEDS` (по умолчанию 20).

**Сначала пилот на 3 сидах** — шесть коротких заданий, которые дают цену
одного сида у каждого подхода:

```bash
NUM_SEEDS=3 ./run_wikipedia.sh stat
```

Когда досчитают, `ГОТОВО! Время` поделить на 3 и умножить на нужное число
сидов. Ориентир по gpt: генерация 5000 текстов — около 230 с на одной карте
плюс ~110 с на метрики, то есть 100 сидов ≈ 9.5 ч. Диффузии дороже: там солвер
на 50 шагов. Сверить с `#SBATCH --time` (40 ч) и с остатком квоты
(`bash projstat.sh proj_1891`).

**Боевой прогон — шесть заданий одной командой:**

```bash
./run_wikipedia.sh stat
```

20 сидов по умолчанию; больше — `NUM_SEEDS=50 ./run_wikipedia.sh stat`.
Шаг сравнения подставляется сам (87500), переопределяется через
`CHECKPOINT_STEP=...`.

**Unconditional — отдельной стадией:**

```bash
./run_wikipedia.sh stat-uncond
```

Он меряется mauve/div/ppl, а не bleu/rouge, то есть в одну таблицу с условными
подходами не ставится, и считается дороже всех. Напоминание: `div` и `ppl` —
абсолютные числа, референс по ним не считается, без floor по `TRG` они не
интерпретируются.

Агрегированные mean ± std и CI сохраняются в
`generated_texts/<prefix>/statistical_eval-*.json`. У guidance в имя файла
входят `gs`, схема классификатора и `time_scale` — три схемы делят
`checkpoints_prefix` с unconditional и иначе перезаписали бы друг друга.

**Проверка после прогона — все подходы обязаны быть на одном шаге:**

```bash
grep -h -A3 'STATISTICAL EVAL SUMMARY' slurm_logs/*-eval_*_stat.log | grep -E 'checkpoint|step'
```

Везде должен стоять один и тот же `87500.pth`.

95% доверительный интервал считается по точной t-критической (`scipy.stats.t`);
прежняя заглушка 1.96 при `df > 30` занижала интервал примерно на 1.2%.

## 5. Два анализа для статьи

### 5.1 Сколько генерация копирует из промпта

diffuseq кладёт латенты промпта прямо в последовательность, и дословное
копирование у него чаще. Копирование надувает bleu и rouge, поэтому без этой
метрики разница между подходами по ним не интерпретируется. Считается
**офлайн по уже сохранённым текстам, GPU не нужен** — запускать на login-ноде:

```bash
python copy_rate.py --step 87500 --out copy_rate-87500.json
```

Колонка `GEN` — доля n-грамм генерации, встречающихся в промпте; `TRG` — то же
для референсного продолжения. Смотреть надо на **избыток** `GEN - TRG`:
референс тоже переиспользует слова промпта, и без этого пола абсолютное число
не читается (та же ошибка, что с `div` и `ppl` у unconditional). Колонка
«макс. кусок» — длина самого длинного дословно скопированного отрезка: средняя
доля не отличает «везде по чуть-чуть» от «один большой кусок целиком».

### 5.2 Свип декодинга у авторегрессионного бейзлайна

У gpt есть температура и `top_p`, у диффузий таких ручек нет. Сравнение с одним
наугад выбранным декодингом рецензент назовёт ослабленным бейзлайном, поэтому в
статью должен идти **лучший** gpt. Семь конфигураций, одна карта, минуты на
каждую:

```bash
./run_wikipedia.sh sweep-gpt
```

Режим генерации входит в имя json (`...-sampling-t0.8-p0.95.json`), так что
прогоны не перезаписывают друг друга. Собрать метрики:

```bash
for f in slurm_logs/*sweep-gpt*.log; do echo "== $f"; grep -aE '^(bleu|bert-score|rouge1|rouge2|rougeL):' "$f" | tail -5; done
```

Выбранный по свипу декодинг потом поставить в `eval_gpt2_stat.sh` через
окружение: `DECODING=sampling TEMPERATURE=... ./run_wikipedia.sh stat`.

## 6. Диагностики: почему classifier guidance не работает

Четыре прогона, которые отвечают на главный вопрос статьи. Все они **только
инференс по уже обученным чекпоинтам**: ничего не обучается, каждое задание
идёт на одной карте и стоит единицы GPU-часов.

`CHECKPOINT_STEP` обязателен ровно по той же причине, что и на стадии `stat`:
без него `restore_parameters` берёт `max(нумерованных)`, а это **разный** шаг у
разных подходов, и диагностика описывала бы не ту модель, что стоит в таблицах.

```bash
CHECKPOINT_STEP=87500 ./run_wikipedia.sh probes
```

Девять заданий. Частями: `probes-window`, `probes-signal`, `probes-geometry`,
`probes-recon`. Одна схема классификатора вместо трёх:

```bash

### 6.1 Окно управления (`probes-window`)

Два края одного интервала по уровню шума.

**`probe_signal_survival.py` — до какого шума классификатор вообще различает
продолжения.** Отвечает на возражение «у вас accuracy 0.95 и нулевой эффект,
значит что-то сломано»: 0.95 — это среднее по всему диапазону curriculum, а
guidance работает на конкретных `t`. Прогон раскладывает точность по `t` и
заодно меряет то, чем guidance пользуется на самом деле — направление
градиента:

| колонка | что это |
|---|---|
| `rank_acc` | доля пар, где логит правильного продолжения выше, чем у чужого при том же промпте и том же шуме. Без калибровки и без порога |
| `cos_grad` | косинус между градиентом guidance и направлением `mu_t*x_0 - x_t`, которое реально ведёт к истинному продолжению |
| `cos_random` | **база сравнения.** В пространстве 64×768 случайный косинус имеет масштаб `1/sqrt(49152) ≈ 0.0045`; без этой колонки `cos_grad` не читается |
| `cos_score` | **потолок.** То же для безусловного score: показывает, что измерение вообще работает |
| `x0_shift` | насколько guidance сдвигает предсказание `x_0`. Отличает «численно невидим» от «двигает, но не туда» |

В конце печатается `tau_signal` — наибольшее `t`, где `rank_acc >= 0.55`
(порог, а не 0.5, потому что при n≈500 стандартная ошибка доли ≈0.022).

Три схемы классификатора считаются вместе намеренно: совпадение кривых у трёх
**разных** классификаторов и есть довод, что дело не в конкретном обучении.

**`probe_commitment.py` — с какого момента менять уже нечего.** Обратный процесс
гоняется до конца со снимками, затем доигрывается из каждого снимка с **другим
сидом**. Если текст после ветвления совпал с исходным — результат в этой точке
предрешён, и любая коррекция score после неё на выход не влияет.
`divergence(t) = 1 - unigram_F1`. В конце печатается `tau_commit`.

`ARCH_TYPE=genie` здесь — **положительный контроль**: у рабочей условной модели
окно обязано быть непустым. Если оно пусто и у неё, измерение сломано и выводы
по `unconditional` ничего не стоят.

> **Главный рисунок статьи** собирается из двух этих json: `accuracy(t)` и
> `divergence(t)` на одной оси шума. Утверждение работы — их носители не
> пересекаются, то есть окно управления пусто и подбор `lambda` не мог помочь
> ни при каком значении.

### 6.2 Геометрия латентного пространства (`probes-geometry`)

`probe_latent_geometry.py` переводит «кластеры с дырами» из интуиции в число.
Основная статистика — **hole ratio**:

```
H(q) = median d(середина отрезка, банк без концов) / median d(точка, ближайший сосед)
```

Концы отрезка из поиска ближайшего **исключены**, и это принципиально: иначе
для близкой пары ответом всегда была бы она сама, и `H` выродился бы в
константу около 0.5 на любых данных. Вопрос стоит так: населён ли **другими**
данными промежуток между двумя объектами. `H` порядка единицы — гладко,
`H` много больше единицы — дыры. Величина безразмерная, поэтому текст и
картинки ложатся на одну ось.

Рядом: `tangent_frac` (доля направления к соседу в касательном подпространстве
по локальному PCA), `local_dim`, `r_tok` (сдвиг латента, на котором декодер
меняет 10% токенов — это бюджет шага guidance) и проба интерполяции
(уверенность декодера на середине отрезка против концов).

Картинки подаются готовым массивом, зависимость от `diffusers` в репозиторий не
тащится. Снять на ноде с интернетом:

```bash
python -c "
import numpy as np, torch
from diffusers import AutoencoderKL
from datasets import load_dataset
vae = AutoencoderKL.from_pretrained('stabilityai/sd-vae-ft-mse').cuda().eval()
ds = load_dataset('detection-datasets/coco', split='val[:2000]')
out = []
for ex in ds:
    im = ex['image'].convert('RGB').resize((256, 256))
    x = torch.from_numpy(np.array(im)).permute(2,0,1)[None].float().cuda()/127.5 - 1
    with torch.no_grad():
        z = vae.encode(x).latent_dist.mean          # [1, 4, 32, 32]
    out.append(z[0].permute(1,2,0).reshape(-1, 4).cpu().numpy())
np.save('image_latents.npy', np.concatenate(out))
"
```

Затем:

```bash
PROBE_IMAGE_LATENTS=$PWD/image_latents.npy CHECKPOINT_STEP=87500 \
    ./run_wikipedia.sh probes-geometry
```

### 6.3 Guidance к одной цели (`probes-recon`) — решающий эксперимент

`probe_recon_guidance.py` различает две версии причины провала:

* **(A) многомодальность цели** — «любое корректное продолжение» задаёт не
  точку, а множество далеко разнесённых мод, и градиент указывает в барицентр;
* **(B) геометрия** — любой шаг, достаточный чтобы изменить выход, выбрасывает
  латент в пустоту между кластерами.

Классификатор заменяется на reconstruction guidance к **одной** фиксированной
цели: механизм тот же (градиент лог-вероятности по `x_t` поверх безусловного
score), но многомодальность равна нулю по построению.

| исход | вывод |
|---|---|
| не работает | дело **не** в многомодальности: даже с идеальной одномодальной целью через это пространство не пройти → побеждает (B) |
| работает | механика исправна, сломана постановка цели → побеждает (A) |
| частично | обе причины, и прогон даёт их количественное разложение |

Режимы цели (`PROBE_TARGET`): `oracle` — истинное продолжение (верхняя
граница); `shuffled` — продолжение соседнего примера (**отрицательный контроль,
он важнее**: если guidance действительно управляет, метрики против истинного
референса обязаны упасть, а против цели, к которой вели, — вырасти);
`json` — генерация другой модели из `generated_texts/<prefix>/*.json`, то есть
практичная двухэтапная схема «сначала выбрать моду, потом вести к ней».

```bash
# двухэтапный вариант: цель берётся из генераций genie
PROBE_TARGET=json PROBE_TARGET_JSON=generated_texts/<prefix>/87500-...json \
ARCH_TYPE=unconditional CHECKPOINT_STEP=87500 sbatch probe_recon_guidance.sh
```

`PROBE_JACOBIAN=identity` (по умолчанию) приближает `dx_0/dx_t ≈ (1/mu_t) I` —
дёшево; `full` делает честный backward через denoising network — вдвое дороже
по шагу, батч приходится уменьшать (`PROBE_BATCH_SIZE=32`).

В выводе две группы метрик: против `TRG` (истинный референс) и против `STEER`
(текст, к которому вели). **Расхождение этих двух групп и есть доказательство,
что механизм управляет.** Если они совпадают — guidance не делает ничего.

**Базовая линия `PROBE_RECON_SCALE=0`** запускается стадией третьим заданием и
обязательна для чтения результата. Это та же безусловная генерация, те же
сиды, то же число текстов и те же метрики, но без всякого guidance. Без неё
непонятно, «BERTScore 0.52» у oracle — это пол безусловной модели или уже
прирост. Строка `guidance` из основной таблицы её не заменяет: там другое число
текстов и другие сиды. При `scale=0` перехват возвращает `None`, а не нулевой
тензор, — иначе обёртка пересчитала бы `x_0` по алгебраической формуле и база
разошлась бы с чистой безусловной генерацией на уровне арифметики с плавающей
точкой (закреплено тестом).

### 6.4 Как следить за прогоном

Все диагностики печатают строки вида `[PROBE +0:12:34] ...` — время от старта
задания. Ожидаемая последовательность:

```
[PROBE +0:00:01] старт: собираю конфиг
[PROBE +0:00:42] собираю модули (BERT, декодер, denoising network)...
[PROBE +0:02:10] восстанавливаю веса из tencdm-...-unconditional (шаг 87500)...
[PROBE +0:03:05] веса готовы: .../87500.pth, шаг 87500
[PROBE +0:03:06] готовлю загрузчик wikipedia/test (препроцессинг может занять десятки минут, это нормально)...
[PROBE +0:21:40] загрузчик готов: 50000 примеров
[PROBE +0:21:41] считаю 168 точек (батчей 8 x сетка 21)
[PROBE +0:22:15] точек сетки 5/168 (3%)  прошло 0:00:34, осталось ~0:18:28
```

**Самый долгий молчаливый участок — подготовка загрузчика.** На wikipedia это
десятки минут, и раньше лог выглядел там зависшим. Теперь вход и выход
отмечены явно: если последняя строка — «готовлю загрузчик», задание работает.

Дальше прогресс идёт по единицам работы, а не по батчам: у
`probe_signal_survival` один батч — это 21 точка сетки и несколько минут,
у `probe_commitment` — 315 шагов солвера. По батчам лог выглядел бы замершим.
`probe_signal_survival` вдобавок печатает после каждого батча промежуточные
`rank_acc` на трёх уровнях шума, так что видно не только что счёт идёт, но и
что он сходится к чему-то осмысленному. На первом батче включается tqdm по
шагам обратного процесса.

Посмотреть вживую:

```bash
tail -f slurm_logs/$(ls -t slurm_logs | head -1)
```

**Промежуточное сохранение.** `probe_signal_survival` и `probe_commitment`
дописывают свой json после каждого батча с полем `"partial": true`; в финале
оно становится `false`. Задание, снятое по лимиту времени, теряет максимум один
батч, а не весь прогон — половина батчей уже даёт читаемую кривую.

**Лимиты времени** заданы с большим запасом (2–4 ч при оценке ~40 мин) и
обоснованы комментарием в каждом `.sh`. Запас намеренный: SLURM списывает
**фактически потраченное** время, а не лимит, поэтому щедрый лимит не стоит ни
одного GPU-часа — он только чуть ухудшает позицию в очереди. А срез по лимиту
стоил бы повторного прогона. Переопределяется на стадии:

```bash
TIME_LIMIT=08:00:00 CHECKPOINT_STEP=87500 ./run_wikipedia.sh probes-recon
```

Проверить, что задания живы и сколько потратили:

```bash
squeue -u $USER -o '%.10i %.22j %.10M %.10l %.8T %R'
```

### 6.5 Guidance с проекцией на касательное (`probes-projected`) — опровергнутая гипотеза

Прогон 24.10 дал факт, из которого всё дальнейшее и следует: классификатор
различает правильное продолжение от чужого с **AUC 0.99 на всём диапазоне
шума**, но косинус его градиента с направлением к истинному продолжению —
**0.009** при СКО случайного косинуса 0.0045 (знаковое среднее 0.0001 базой
быть не может: оно сходится к нулю с ростом выборки, см. 6.1). Градиент вдвое
лучше случайного и при
этом на 99% ортогонален нужному направлению.

Гипотеза: ортогональная часть — это движение **прочь с многообразия**. Отсюда и
невозможность поднять λ: ортогональная компонента разрушает сэмпл раньше, чем
касательная накопит полезный сдвиг (в ВКР при λ≥5000 все метрики обваливались).

`probes/manifold.py` оценивает локальное касательное подпространство локальным
PCA по k соседям из банка чистых латентов, `probe_projected_guidance.py`
проецирует на него градиент.

```bash
CHECKPOINT_STEP=87500 ./run_wikipedia.sh probes-projected
```

Четыре задания: `raw`, `tangent`, `normal` при **одной доле шага** плюс пол без
guidance.

> **Почему именно при одной доле шага.** Проекция уменьшает норму градиента в
> разы. Сравнивать `raw` с `tangent` при одной λ значило бы сравнивать разные
> размеры шага, а не разные направления. Поэтому `PROBE_SCALE_MODE=adaptive`:
> λ_t подбирается на каждом шаге так, чтобы `||λ_t·grad||/||score||` равнялось
> `PROBE_TARGET_RATIO`. Это нужно и само по себе — замер показал, что при
> постоянной λ=10 эта доля гуляет вдоль траектории **в 170 раз** (0.0001 при
> t=0.01 против 0.017 при t=0.8).

> **Режим `normal` — не формальность.** Если выигрыш даёт не касательное
> направление, а просто уменьшение шага, то `normal` при той же доле покажет то
> же самое. Без этого контроля `tangent` ничего не доказывает.

Свип силы и проверка множителя:

```bash
CHECKPOINT_STEP=87500 ./run_wikipedia.sh probes-sweep
```

```bash
CHECKPOINT_STEP=87500 ./run_wikipedia.sh probes-sigmoid
```

`probes-sigmoid` проверяет факт, что множитель `(1−σ(f))` в точной формуле
`∇log σ(f)` обнуляет guidance там, где классификатор уверен, — а уверен он при
**малом** шуме, где AUC 0.9997 и где текст и решается (доля шага там 0.0001).
`PROBE_SIGMOID=0` ведёт по `∇f` без множителя.

**Как читать `tan_grad`.** В `probe_signal_survival` появились колонки
`tan_grad` / `tan_score` / `tan_random` — доля энергии в касательном
подпространстве. Читается **только** относительно `tan_random = dim/D`
(при `PROBE_TANGENT_DIM=16` это 16/768 ≈ 0.021). `tan_grad` на уровне
`tan_random` означает, что градиент неотличим от случайного направления, то
есть просто уводит с многообразия.

### 6.6 Ось информативности условия (`probes-infoaxis`) — результаты и исправление оси

Прогон 24.10, шестнадцать заданий, **обучать ничего не нужно**: все условия
получены деградацией оракульной цели.

```bash
CHECKPOINT_STEP=87500 ./run_wikipedia.sh probes-infoaxis
```

| режим | что варьируется | характер информации |
|---|---|---|
| `none` | — | полная цель, верхняя точка оси |
| `prefix` | k открытых позиций | **точная** о немногих позициях |
| `quantize` | K центроидов по позициям | **грубая** обо всех позициях |
| `seqquant` | K центроидов по последовательностям | «веди к теме» |
| `dilute` | доля информации (проценты) | непрерывная, сжатие к среднему |
| `noisy` | уровень шума (проценты std) | непрерывная, изотропная порча |
| `rank` | r главных компонент | грубая, по подпространству |

#### Что измерено

| условие | уровень | цель_vs_истина | bert | bleu |
|---|---|---|---|---|
| `none` (оракул) | — | 0.998 | **0.980** | 0.938 |
| `prefix` | 1 → 32 | 0.998 (маска) | 0.371 → **0.722** | 0.0001 → 0.512 |
| `quantize` | 2 → 512 | 0.241 → 0.471 | 0.452 → **0.580** | 0.000 → 0.076 |
| `seqquant` | 4 → 64 | 0.307 → 0.320 | 0.390 → **0.408** | 0.001 → 0.022 |
| пол (без guidance) | — | — | 0.4605 | 0.00195 |
| реальный классификатор | 1 бит | ≈ пол | 0.5081 | 0.0098 |

#### Ось x была выбрана неверно

Запланированная проверка «ложится ли точка (0.009, 52%) на кривую» **не
выполнима в исходном виде**: косинус, которым мерилось выравнивание, измеряет
не информативность условия.

| условие | `cos_to_true` | bert |
|---|---|---|
| оракул (полная цель) | 0.0909 | 0.980 |
| `quantize` K=2 (почти пусто) | **0.1775** | 0.452 |
| `prefix` k=1…16 | отрицательный | 0.371 → 0.606 |

У полной цели косинус **вдвое ниже**, чем у почти пустой квантизации, а у
`prefix` он отрицателен при монотонно растущем качестве. Причина: величина
считалась в пространстве `x_t` как `cos(g, mu·true − x_t)`, а при `t → 1`
`mu ≈ 5·10⁻⁹` (CosineSD d=9, float32), поэтому `mu·true − x_t ≈ −x_t`.
«Направление к истине» вырождается в «убрать шум», и косинус с ним тем выше,
чем ближе цель к среднему данных. Центроиды лежат у среднего — они и выигрывают.

Исправление: выравнивание считается в пространстве `x_0`,
`cos_x0 = cos(z − x̂₀, true − x̂₀)`. Для оракула это 1 по построению, масштаб
`mu` в него не входит. Старая величина сохранена в json как `cos_to_true` —
это задокументированный отрицательный результат по диагностике, а не ось.

#### Рабочая ось: восстановимость цели

Информативность условия измеряется тем же, чем качество: насколько сама
деградированная цель похожа на истину (`цель_vs_истина`, колонка
`target_recovery` в json). По этой оси картина чистая и монотонная, наклон
около единицы, **причём генерация идёт выше восстановимости цели**
(0.419 → 0.525): диффузия не просто переносит условие, она доводит его до
многообразия текста.

> **Номинальные биты качество не предсказывают.** `prefix` k=32 и `quantize`
> K=32 оба дают ~320 бит, а bert 0.722 против 0.470 — разница больше, чем весь
> диапазон от пола до cross-attention. Значит правильный инвариант —
> **достижимое восстановление цели**, а не счёт бит. Это методический
> результат: ось строится по измеримой величине, а не по подсчёту.

#### Главный факт, который надо объяснить

Точка-цель информативностью ~2 бита (`seqquant`) даёт bert 0.390–0.408, то есть
**ниже пола 0.4605**: вести к плохой точке хуже, чем не вести никуда. Реальный
бинарный классификатор несёт **один** бит и даёт 0.5081 — **выше пола**.

Один бит обыгрывает два бита на порядок величины эффекта. Значит дело не только
в объёме информации, но и в **форме** условия: классификатор задаёт множество
допустимых продолжений, а не точку. Это проверяется в 6.8 и, если
подтверждается, становится главным утверждением работы.

Собрать ось:

```bash
for f in probe_results/information_axis-*.json; do python -c "import json,sys;d=json.load(open(sys.argv[1]));m=d['metrics'];print(f\"{d['degrade']:9} {d.get('set_shape','-'):9} L={d['level']:<5} цель={d['target_recovery']['bert-score']:.4f} bert={m['bert-score']:.4f} bleu={m['bleu']:.5f} cos_x0={d.get('cos_x0')}\")" "$f"; done | sort -t= -k2 -n
```

Сортировка по `цель=` — это и есть ось x. Качество обязано расти вместе с ней.

**k-means инициализируется по k-means++, а не случайными точками.** На
синтетике из трёх разнесённых кластеров случайная инициализация ставила два
центроида в один кластер, и уровень K=3 давал фактически две группы. Для оси
это хуже обычного шума: уровни перестают соответствовать объёму информации.
Закреплено тестом.

**Банк последовательностей задаётся отдельно (`PROBE_SEQ_BANK`, по умолчанию
1024).** Бюджет банка `PROBE_BANK` считается в позициях, и при 8192 позициях
целых продолжений набиралось всего 192 — `seqquant` с K=256 падал с
«центроидов (256) не меньше точек банка (192)». Закреплено тестом на все
запуски `seqquant` разом.

### 6.7 Непрерывная ось информативности (`probes-dilute`)

Дискретные режимы 6.6 монотонны, но **не покрывают тот диапазон, где живёт
классификатор**: его условие несёт один бит, то есть восстановимость цели на
уровне пола 0.4605, а `seqquant` дал 0.307–0.320 (ниже пола), `quantize` —
0.355 и выше. Сравнивать классификатор по-прежнему не с чем.

```bash
CHECKPOINT_STEP=87500 ./run_wikipedia.sh probes-dilute
```

Двенадцать заданий, две непрерывные оси:

| режим | формула | почему именно так |
|---|---|---|
| `dilute` | `z = mean + a·(target − mean)` | так выглядит **условное среднее** истины при частичной информации: байесовская оценка по b битам — сжатая копия истины. Не произвольная порча, а каноническая форма «условие несёт долю информации» |
| `noisy` | `z = target + s·std·ε` | вторая ось, другая по характеру порчи |

> **Зачем две.** Если обе лягут на одну кривую «качество от восстановимости
> цели», значит качество определяется **объёмом** информации, а не способом её
> порчи. У пары `prefix`/`quantize` этого вывода сделать нельзя: они
> дискретны и почти не перекрываются по диапазону, а по номинальным битам
> вообще расходятся втрое (см. 6.6).

Низкие уровни `dilute` (1%, 2%) дают цель чуть информативнее пола — **ровно
регион классификатора**. Это и есть точка, где кривая либо проходит через
(≈пол, 0.5081), либо нет. Закреплено тестом: без низких уровней стадия
бессмысленна.

### 6.8 Множество против точки при равной информации (`probes-set`) — решающий замер

Объясняет факт из 6.6: один бит классификатора (0.5081, выше пола) обыгрывает
два бита точки-цели (0.390–0.408, ниже пола).

```bash
CHECKPOINT_STEP=87500 ./run_wikipedia.sh probes-set
```

Шесть заданий: два уровня тем (K=16, 64) на три формы условия. Информация у
всех трёх **одинакова** — метка кластера, log₂K бит:

| форма | что подаётся | где лежит |
|---|---|---|
| `centroid` | среднее кластера | **вне** многообразия |
| `medoid` | самый центральный реальный элемент кластера | **на** многообразии |
| `mixture` | мягкий минимум по M кандидатам кластера | множество на многообразии |

Разложение эффекта:

* `centroid → medoid` — **цена схода с многообразия**;
* `medoid → mixture` — **выигрыш множественной формы** при той же информации.

> **Информация не утекает.** Медоид и кандидаты выбираются по близости к
> **центроиду**, а не к истине. Если бы медоид выбирался по истине, он нёс бы
> больше метки кластера, и множество выигрывало бы просто потому, что ему
> подсказали ответ. Закреплено тестом: две разные цели из одного кластера
> обязаны получить одинаковые центроид, медоид и набор кандидатов.

STEER (и значит `target_recovery`) для `medoid` и `mixture` **один и тот же** —
медоид, лучшая одиночная реализация метки кластера. То есть у двух режимов
совпадает и информация, и достижимое восстановление цели, а отличается только
форма guidance. Именно это делает сравнение контролируемым.

Если `mixture` обыгрывает `medoid`, различие «множество против точки» доказано
**внутри работы**, а не только сравнением с классификатором. Тогда главное
утверждение формулируется так: guidance от дискриминативного сигнала и guidance
к цели-реконструкции — качественно разные операторы; первый деградирует с
информацией плавно, второй — катастрофически.


### 6.9 Починка масштаба шага у `probe_recon_guidance`

Первый прогон (24.10) был **невалиден**: `||scale·grad||/||score|| = 4·10⁶`,
обе генерации — мусор. Причина: в режиме `identity` градиент равен
`(z − x̂₀)/(γ²·μ_t)`, а у CosineSD с d=9 при t→1 выходит `μ_t ≈ 4.8·10⁻⁹`, то
есть `1/μ_t ≈ 2·10⁸`. Первый же шаг траектории уничтожал всё.

Теперь сила задаётся долей шага, как и у projected: `PROBE_SCALE_MODE=adaptive`
(по умолчанию) и `PROBE_TARGET_RATIO`. **Базовая линия теперь
`PROBE_TARGET_RATIO=0`, а не `PROBE_RECON_SCALE=0`** — при адаптивном режиме
нулевой `scale` guidance не выключает.

### 6.10 Страж дублирования цикла генерации

Обратный процесс в `probes/common.py` продублирован ради перехватов (ветвление,
подмена градиента, снимки). Расхождение с боевым `pred_embeddings` было бы
тихим и обесценило бы все диагностики, поэтому оно закрыто тестом:

```bash
python -m pytest tests/test_probes.py -v
```

`test_reverse_process_reproduces_pred_embeddings` требует **побитового**
совпадения при одном сиде на всех трёх подходах. Порядок обращений к генератору
случайных чисел здесь часть контракта: сначала `prior_sampling` на CPU, затем по
одному `randn_like` на каждом шаге солвера.
